## BUG-001 — `nimbus diag --json` wraps JSON with Clack banner

**Severity:** low. Cosmetic for human stdout; breaks any programmatic JSON consumer (`ConvertFrom-Json`, `jq`, the smoke run sheet).
**Surface:** CLI — `nimbus diag --json` (and any other JSON-emitting CLI command).
**Status:** fixed in `packages/cli/src/index.ts` — `intro`/`outro` are now gated behind `isQuiet = !stdout.isTTY || argv.includes("--json") || NIMBUS_QUIET=1`. Regression coverage in `packages/cli/test/integration/cli-banner-suppression.integration.test.ts`.
**First seen:** smoke run, 2026-05-07, Windows 11 / PowerShell 7.

### Repro

```powershell
& 'C:\gitrepo\Nimbus\packages\cli\dist\nimbus.exe' diag --json | ConvertFrom-Json
```

Yields:

```
ConvertFrom-Json: Conversion from JSON failed with error: Unexpected character encountered while parsing value...
```

The actual stdout is:

```
[90mT[39m  Nimbus
{
  "gateway": { ... },
  ...
  "auditLogTail": []
}
[90m|[39m
[90m—[39m  Done.
```

The Clack-style `intro("Nimbus")` header and `outro("Done.")` footer (with ANSI escapes) wrap the JSON body, so any non-human consumer chokes on the surrounding non-JSON content.

### Root cause

`packages/cli/src/index.ts:104` calls `intro("Nimbus")` unconditionally before `dispatchCommand`, and line 134 calls `outro("Done.")` in the `finally` block after every command. No suppression for `--json` flags, piped stdout, or non-interactive shells.

### Fix sketch

Suppress `intro`/`outro` when stdout is not a TTY, when any arg matches `--json`, or when `NIMBUS_QUIET=1`. Smallest change:

```ts
// packages/cli/src/index.ts
const isQuiet =
  !process.stdout.isTTY ||
  rawArgv.includes("--json") ||
  process.env.NIMBUS_QUIET === "1";

if (!isQuiet) intro("Nimbus");
// ... command dispatch ...
if (!isQuiet) outro("Done.");
```

Detecting non-TTY stdout is the most defensible default — pipes and redirections always want clean output regardless of the per-command flag. The `--json` arg check is belt-and-braces for users who pipe through a tool that still claims a TTY.

### Workaround until fixed

Banner-stripping idiom in PowerShell:

```powershell
$raw  = (& nimbus diag --json) -join "`n"
$json = $raw.Substring($raw.IndexOf('{'), $raw.LastIndexOf('}') - $raw.IndexOf('{') + 1) | ConvertFrom-Json
```

This relies on the JSON body being a single top-level object, which is true for `diag.snapshot` and `diag.slowQueries`.

### Verification

- After fix: `nimbus diag --json | ConvertFrom-Json` succeeds with no preamble stripping.
- After fix: `nimbus diag` (interactive) still shows the Nimbus banner header and `Done.` footer.
- Add a unit/integration test that runs `nimbus diag --json` with `process.stdout.isTTY = false` and asserts the captured stdout starts with `{` and ends with `}` (no banner bytes).

## BUG-002 — `nimbus data export` deadlocks waiting for HITL consent

**Severity:** high. The CLI hangs forever; the only escape is Ctrl+C, and the Gateway is left with a stranded pending HITL request. Any user following the Phase 4 acceptance criterion ("`nimbus data export` ... restores full functionality on a fresh machine") hits this immediately.
**Surface:** CLI — `nimbus data export`. Likely affects `nimbus data import` and `nimbus data delete` for the same reason (each has a server-side gate but no consent handler in the CLI command).
**Status:** fixed. `packages/cli/src/commands/data.ts` `withClient` now registers a consent handler before the IPC call: `registerConsentPromptHandler` for interactive runs, `registerAutoApproveConsentHandler` (new) when `--yes` is passed. `--yes` is now accepted by `data export` and `data import` (delete already had it). Regression coverage in `packages/cli/src/lib/interactive-ipc-handlers.test.ts`.
**First seen:** smoke run, 2026-05-07, Windows 11 / PowerShell 7.

### Repro

```powershell
nimbus start
& 'C:\gitrepo\Nimbus\packages\cli\dist\nimbus.exe' data export --output .\nimbus-backup-smoke.tar.gz --passphrase "smoke-test-passphrase-strong-1!"
```

CLI prints the Clack banner header (`T  Nimbus`) and then hangs indefinitely. No timeout. Gateway logs show a pending HITL request emitted but never responded to.

### Root cause

`data.export` is HITL-gated server-side at `packages/gateway/src/ipc/data-rpc.ts:72`:

```ts
const gateResult = await executor.gate({
  type: "data.export",
  payload: { output, includeIndex },
});
```

`executor.gate(...)` emits a `consent.request` IPC notification and awaits `consent.respond`. The CLI side, in `packages/cli/src/commands/data.ts:43-55`, does:

```ts
await withClient(async (client) => {
  const result = await client.call<...>("data.export", { ... });
  console.log(`[ok] wrote bundle to ${result.outputPath}`);
  ...
});
```

`withClient` opens an `IPCClient`, calls the method, and disconnects. It never registers a consent handler. Compare with `packages/cli/src/lib/interactive-ipc-handlers.ts` which provides `registerConsentPromptHandler(client)` — used by the TUI and other interactive commands but not by `data.ts`. Result: Gateway waits forever for `consent.respond`, CLI waits forever for the IPC response, deadlock.

The same shape applies to `runDataImportCli` and `runDataDeleteCli` in the same file — both call gated server methods and neither registers consent.

### Fix sketch

Wire the consent handler into `withClient` (or a sibling helper) so every `data.*` command accepts terminal-prompted consent:

```ts
import { registerConsentPromptHandler } from "../lib/interactive-ipc-handlers.ts";

async function withClient<T>(fn: (c: IPCClient) => Promise<T>): Promise<T> {
  const paths = getCliPlatformPaths();
  const state = await readGatewayState(paths);
  if (state === undefined) throw new Error("Gateway is not running. Start with: nimbus start");
  const client = new IPCClient(state.socketPath);
  await client.connect();
  registerConsentPromptHandler(client);  // <-- add this
  try {
    return await fn(client);
  } finally {
    await client.disconnect();
  }
}
```

Also add a `--yes` / `--assume-yes` flag for non-interactive use (CI, scripts). When set, the CLI registers a consent handler that auto-approves with a warning printed to stderr and an entry in the local audit log.

### Workaround until fixed

There is no working CLI workaround for the export — the gate is structural. Options:

1. Kill the CLI with Ctrl+C (multiple presses on Windows). Run `nimbus stop && nimbus start` afterwards to drop the stranded HITL request from the Gateway's pending queue.
2. For the smoke run: `data export` is **not actually exercised** by the trimmed `v0.1.0` checklist — that section moved to `manual-smoke-desktop.md`. The backup-file precondition is stale; skip it. (Updated in `manual-smoke-v0.1.0.md` and the run sheet.)

### Verification

- After fix: `nimbus data export ...` prompts the user with a Clack confirm dialog; entering yes proceeds and writes the bundle, no proceeds and aborts cleanly without leaving a stranded HITL request.
- After fix: `nimbus data export --yes ...` writes the bundle without prompting and emits a stderr warning + an audit-log entry.
- Add an e2e CLI test under `packages/gateway/test/e2e/scenarios/data-export-cli.e2e.test.ts` that drives the CLI subprocess against a mock Gateway, asserts the consent prompt appears, and asserts the export completes when the prompt is approved.

## BUG-003 — TUI Connector Health pane stuck on "loading…"

**Severity:** medium. The smoke §1.1 verification "google_photos shows degraded in ConnectorHealth pane" is impossible to satisfy — the pane never renders any rows. Cosmetically the pane stays on the placeholder "loading…" indefinitely, which is also what BUG-004 covers.
**Surface:** CLI — TUI `ConnectorHealth.tsx`. Likely also affects any code path or test that assumes `connector.list` is a real Gateway method.
**Status:** fixed. `packages/cli/src/tui/ConnectorHealth.tsx` now polls `connector.listStatus` and parses the real `SyncStatus` shape (`{ serviceId, status: ok|syncing|paused|backoff|error }`); glyphs map ok→●, syncing/paused→◐, backoff/error→○. Tests in `ConnectorHealth.test.tsx` and `App.test.tsx` were aligned to the real method+shape so future drift fails CI.
**First seen:** smoke run, 2026-05-07, Windows 11 / PowerShell 7.

### Repro

```powershell
nimbus start
nimbus tui
# Right column: 'Connectors' label + 'loading…', forever.
```

`google_photos` paused via §0.2; `nimbus connector list` from the CLI shows it correctly. The TUI pane never updates.

### Root cause

Two compounding mismatches between the TUI and the Gateway:

1. **Wrong method.** `packages/cli/src/tui/ConnectorHealth.tsx:65`:
   ```ts
   const poll = useIpcPoll<unknown>("connector.list", STATUS_POLL_INTERVAL_MS, mode);
   ```
   The Gateway dispatcher (`packages/gateway/src/ipc/connector-rpc.ts:60-124`) has no `connector.list` case — only `connector.listStatus`, `connector.status`, etc. The dispatcher returns `{ kind: "miss" }`, which surfaces as a JSON-RPC method-not-found error; `useIpcPoll` swallows it and leaves `data = null`.

2. **Wrong shape.** Even if the method name were corrected, the parser expects:
   ```ts
   interface ConnectorRow { service: string; status: "ok" | "degraded" | "down"; }
   ```
   The actual `connector.listStatus` returns `SyncStatus[]` (`packages/gateway/src/sync/types.ts:107-124`):
   ```ts
   { serviceId: string; status: "ok" | "syncing" | "paused" | "backoff" | "error"; ... }
   ```
   Field name (`service` vs `serviceId`) and status enum both differ. `isConnectorRow` rejects every row; `rows.length === 0`; pane renders `(none)`.

3. **Why the unit tests didn't catch it.** `packages/cli/src/tui/App.test.tsx:95` stubs `results: { "connector.list": [], "watcher.list": [] }` — empty arrays that always render the empty-list path. The stub key matches what the TUI calls, not what the Gateway actually exposes; no integration test exercises the real method-name + shape contract.

### Fix sketch

Two changes in `ConnectorHealth.tsx`:

```ts
// 1. Use the real method.
const poll = useIpcPoll<unknown>("connector.listStatus", STATUS_POLL_INTERVAL_MS, mode);

// 2. Update the parser to match SyncStatus.
interface ConnectorRow {
  serviceId: string;
  status: "ok" | "syncing" | "paused" | "backoff" | "error";
}

function isConnectorRow(row: unknown): row is ConnectorRow {
  if (typeof row !== "object" || row === null) return false;
  const r = row as Record<string, unknown>;
  return (
    typeof r["serviceId"] === "string" &&
    (r["status"] === "ok" ||
      r["status"] === "syncing" ||
      r["status"] === "paused" ||
      r["status"] === "backoff" ||
      r["status"] === "error")
  );
}

function glyph(status: ConnectorRow["status"]): string {
  if (status === "ok") return "●";
  if (status === "syncing" || status === "paused") return "◐";
  return "○";   // backoff, error
}
```

Update `App.test.tsx` and `ConnectorHealth.test.tsx` to stub `connector.listStatus` with realistic `SyncStatus`-shaped rows. Add an integration test (Bun subprocess Gateway + real TUI render) that renders one healthy + one paused connector and asserts both glyphs appear.

To prevent recurrence: add a static-time check (script under `scripts/structure-audit/`) that scans `useIpcPoll<...>("<method>", ...)` calls in `packages/cli/` and asserts each method name appears in the Gateway dispatch tables. This is the kind of cross-package contract drift that invariant-style audits catch; the existing B3 audit already enforces I1 / vault-key allow-lists in a similar style.

### Workaround until fixed

None. The TUI Connector Health pane is non-functional. For the smoke run, mark §1.1 "google_photos shows degraded in ConnectorHealth pane" as 🚧 and link this bug.

### Verification

- After fix: launching `nimbus tui` after `nimbus connector pause google_photos` shows `google_photos` with the "paused" glyph (◐) within `STATUS_POLL_INTERVAL_MS`.
- After fix: after `nimbus connector unpause google_photos`, the glyph returns to "ok" (●) within one poll interval.
- Static check (new): `bun scripts/structure-audit/check-tui-ipc-methods.ts` exits non-zero when the TUI references an IPC method name not present in the Gateway dispatcher.

## BUG-004 — TUI right-pane is visually lost on wide terminals; labels lack context

**Severity:** low. Pure UX polish, no functional regression. Surfaced because the user reading the TUI for the first time could not tell what the right-pane lines were ("what are all those lines on the right side?").
**Surface:** CLI — TUI `App.tsx`, `ConnectorHealth.tsx`, `WatcherPane.tsx`, `SubTaskPane.tsx`.
**Status:** fixed. The right pane now ships with `borderStyle="single" borderColor="gray" paddingX={1}` so it reads as one visual unit. The left `ResultStream` pane width is capped at `Math.min(max(cols-32, 40), 120)` so on a 250-col terminal the right pane sits adjacent instead of floating at the far edge. Empty-state copy across the three panes was rewritten as full sentences ("Loading connector status…", "No connectors registered", "No watchers configured", "No sub-tasks running yet") and a one-line `Ctrl+C twice to exit` footer was added so first-time users have an exit anchor. Regression coverage in `ConnectorHealth.test.tsx`, `WatcherPane.test.tsx`, `SubTaskPane.test.tsx`, and `App.test.tsx`.
**First seen:** smoke run, 2026-05-07, Windows 11 / PowerShell 7 (Windows Terminal at ~250 columns).

### Repro

```powershell
nimbus tui
# Resize the terminal to 200+ columns. Observe the layout:
#
#   nimbus>                                                                      Connectors
#                                                                                loading…
#                                                                                Watchers
#                                                                                0 active, 0 firing
#                                                                                Sub-Tasks
#                                                                                No active sub-tasks
```

Symptoms:

- **No visual separator.** `App.tsx:329-338` renders the row split as `<Box flexDirection="row">` with `flexGrow={1}` left + `width={30}` right, no border. On wide terminals the empty `ResultStream` becomes hundreds of columns of whitespace and the right pane visually floats orphaned at the right edge.
- **Bare pane labels.** `Connectors`, `Watchers`, `Sub-Tasks` are just bold text with no glyph or framing. A first-time user cannot tell whether they are click-targets, log lines, or live status.
- **Ambiguous placeholder copy.** `loading…` in `ConnectorHealth.tsx:47` does not say *what* is loading; `0 active, 0 firing` and `No active sub-tasks` give no hint of what a non-zero state would look like.

### Root cause

UX cost of the WS6 design choice to keep the panes lightweight (no Ink borders, no tooltips, no help line). Was acceptable when the assumption was "users start on a ~120 column terminal" — falls apart on wide modern terminals where horizontal whitespace is the dominant visual element.

### Fix sketch

Three small changes, scoped to the three pane components and the layout in `App.tsx`:

1. **Border the right pane** so it reads as one visual unit:
   ```tsx
   <Box flexDirection="column" width={30} borderStyle="single" borderColor="gray" paddingX={1}>
   ```

2. **Cap the left pane's flexGrow** so the gap stops growing past a reasonable width. Bound via `width={Math.min(cols - 32, 120)}` (or similar) so on a 250-col terminal the left pane stops at 120 cols and the right pane sits closer to the prompt.

3. **Improve placeholder copy.** `Loading connector status…` / `No watchers configured` / `No sub-tasks running yet` (instead of `loading…` / `0 active, 0 firing` / `No active sub-tasks`). Tiny strings, big readability win.

4. **Bottom help line.** Add a one-line footer listing `Ctrl+C twice to exit · ? for help` so new users have an anchor.

### Workaround until fixed

Resize the terminal narrower (≤ 100 cols) so the layout collapses to single-column.

### Verification

- After fix: on a 200-col terminal, the right pane has a visible border and sits within ~120 cols of the prompt.
- After fix: empty-state copy reads as full English sentences, not bare numbers.
- After fix: the `narrow` collapse path (terminal < 100 cols) still works as documented in the smoke checklist §1.6.

## BUG-005 — TUI multi-turn memory broken

**Severity:** high. The TUI is the headline `v0.1.0` agent surface; if every turn is a fresh, contextless run, the agent surface is functionally single-turn. Every UX flow that requires the user to *answer a question* the agent asked breaks.
**Surface:** engine + CLI / TUI `App.tsx` (`engine.askStream` call site).
**Status:** fixed (four layers, third + fourth landed in a follow-up after the first round shipped). (1) `packages/cli/src/tui/App.tsx` mints a `sessionIdRef` (via `crypto.randomUUID()`) once per TUI process and threads it on every `engine.askStream` call. (2) `packages/gateway/src/engine/run-ask.ts` auto-appends both the user input and the assistant reply to `SessionMemoryStore` after the conversational turn returns (when `sessionId` is in the request context), and loads the last 12 turns BEFORE the next agent invocation. (3) `packages/gateway/src/engine/run-conversational-agent.ts` accepts a `priorTurns` array and, when non-empty, passes a `[...priorTurns, currentInput]` messages array to `agent.stream`/`generate` instead of a raw string prompt — the LLM now sees the conversation history. New `SessionMemoryStore.getRecentTurns(sessionId, limit)` exposes the chronological tail. **Follow-up (BUG-005-b):** when the user re-tested in their runtime, multi-turn memory still didn't work because the embedding worker had failed to initialize on their machine ("embedding worker failed to initialize; semantic search disabled"), causing `assemble.ts` to skip creating `SessionMemoryStore` entirely (`if (rt == null) return undefined`) and `SessionMemoryStore.append()` to silently no-op even when called (its `if (vec?.length !== this.dims) return` early-return). Multi-turn replay needs literal turn storage, not embeddings; the two were over-coupled. The follow-up commit (a) `assemble.ts` now instantiates `SessionMemoryStore` with a null-returning `embedText` fallback when the runtime is unavailable, and (b) `SessionMemoryStore.append()` now records the row anyway with `vec_rowid=0` sentinel when embedding is null/wrong-dim, so `getRecentTurns()` can replay it. Semantic `recall()` still requires a real embedding (its INNER JOIN naturally skips sentinel rows). Regression coverage in `packages/cli/src/tui/App.test.tsx`, `packages/gateway/src/engine/run-ask.test.ts`, `packages/gateway/src/engine/run-conversational-agent.test.ts`, and `packages/gateway/src/memory/session-memory-store.test.ts` (including the new "append still records the literal turn when embedText returns null" case). A diagnostic at `scripts/diagnose-bug-005.ts` reads `nimbus.db` directly and reports which of the layers (schema, vec, append, runAsk) is broken — useful when this regresses again.
**First seen:** TUI sanity, 2026-05-08, Windows 11 / PowerShell 7, on the `dev/asafgolombek/v0.1.0-engine-smoke-bugs` branch immediately after merging the BUG-003/BUG-004 fixes.

### Repro

```
nimbus> draft a gmail to my own address summarising what I did this week
[agent] ⚠️ A few things before I send — what email should I send this to?
nimbus> asafgolombek@gmail.com
[agent] I can see you've entered an email address. How can I help you? Are you looking to:
        1. Find a person associated with this email in the local index?
        2. Search for activity (PRs, issues, messages, files) linked to this person?
```

The agent's turn-1 output explicitly asked "what email?" and the user answered with the address. Turn 2 should have continued the email-drafting flow with that address. Instead the agent treats the bare email as a brand-new query, with no awareness of the prior question.

### Root cause (hypothesis — pending investigation)

`packages/cli/src/tui/App.tsx` calls:

```ts
const res = await client.call<{ streamId: string }>("engine.askStream", {
  input: query,
});
```

No `sessionId` is passed. If `engine.askStream` defaults to a fresh session per call (or if the engine ignores session continuity altogether for streaming), every turn is a new run with no prior conversation in the LLM context. Confirm by tracing `engine.askStream` in `packages/gateway/src/ipc/engine-rpc.ts` and `packages/gateway/src/engine/agent.ts` — does it accept and consume a `sessionId` param, and does the TUI thread one across turns?

The Gateway has session memory (`packages/cli/src/commands/session.ts` references `Session RAG memory` — list/clear/recall), so the durable persistence path likely exists. The TUI just isn't wired to it.

### Fix sketch (provisional)

1. Hold a `sessionId` in the TUI reducer (mint on first submit, persist for the lifetime of the TUI process or until `Nimbus: New Conversation`).
2. Pass `{ input, sessionId }` to `engine.askStream`.
3. Audit `engine-rpc.ts`: confirm the param is accepted; if not, plumb it through to the agent so the LLM receives the prior turns from session memory.
4. Add a regression test that submits two prompts in the same TUI render, asserts the second `engine.askStream` call carries the same `sessionId` as the first.

### Workaround until fixed

Re-state the full context in every turn ("draft a gmail to asafgolombek@gmail.com summarising my week"). Awkward, but functional.

### Verification

- After fix: a turn-2 prompt of just `asafgolombek@gmail.com` after a turn-1 "what email?" continues the prior flow rather than being treated as a fresh query.
- Static check: `grep "engine.askStream" packages/cli/src/tui/` shows the call site passes `sessionId`.
- E2E: `packages/gateway/test/e2e/scenarios/tui-multi-turn-memory.e2e.test.ts` (new) drives two prompts in one session, asserts the second prompt sees the first prompt + agent reply in its prompt context.

## BUG-006 — Agent contradicts itself about its own tools across turns

**Severity:** high. Agent gaslights the user about whether a capability exists. Combined with BUG-005, the user wastes turns trying to convince the agent to do something it can do but is denying. Erodes the entire "intelligent local agent" claim of `v0.1.0`.
**Surface:** engine / agent — likely `packages/gateway/src/engine/agent.ts` (Mastra agent setup) or wherever the tool list is composed for an `engine.askStream` invocation.
**Status:** fixed as a consequence of the BUG-005 memory fix. Investigation traced the contradiction to a missing prior-turn context: each turn was a fresh agent invocation with no awareness of the previous request, so tool relevance was decided per-prompt by the LLM's interpretation of the current input alone. With prior turns now flowing into the agent (BUG-005 layers 1–3), the agent sees turn 1's "draft a gmail" framing when it processes turn 3's "send me a summery" — gmail tools stay in scope. The tool list itself was never the issue; the prompt context was.
**First seen:** TUI sanity, 2026-05-08, Windows 11 / PowerShell 7.

### Repro

Same TUI session as BUG-005.

- **Turn 1** (user: `draft a gmail to my own address …`):
  > "Sending an email is an **irreversible action**. I want to make sure you're happy with the content before I do so."
  > Agent asks for the email address and confirmation, implying it intends to send.
- **Turn 3** (user: `i gave you my email so you could semd me a summery of my last week`):
  > "I want to be straightforward with you — I don't have the ability to **send emails**. … I don't have an email-sending tool available."

Direct contradiction. Meanwhile the right pane's Connector Health view shows `● gmail` (status `ok`) — the tool surface is healthy and registered.

### Root cause (hypothesis — pending investigation)

Two candidate explanations, not mutually exclusive:

1. **Tool list drifts between turns.** The agent's available-tools array is recomputed each turn and turn 3 is missing `gmail.*`. Could happen if tool selection is dynamic per query (intent classifier hides gmail when the input doesn't look like an email task) or if tool registration races with the request handler.
2. **System prompt drifts between turns.** The role description / "you have access to these tools" preamble differs between calls. Without session memory (BUG-005), each turn is a fresh agent invocation and any non-deterministic system-prompt construction (sampled examples, randomized capability list) would produce divergent behavior.

Trace one full `engine.askStream` request end-to-end: capture the exact tool list and system prompt sent to the LLM in turn 1 vs turn 3, diff them, identify which differ and why.

### Workaround until fixed

None reliable. The user can re-prompt with explicit task framing ("use the gmail tool to send this") which sometimes recovers the capability, but the contradiction itself is unfixable from the user side.

### Verification

- After fix: in any single TUI session, the agent's claim about whether `gmail` (or any healthy connector's) tools are available is consistent across turns.
- Diagnostic: a Gateway audit log entry per `engine.askStream` recording the tool-name list passed to the LLM. Diffing log lines makes "the list shrank between turns" detectable.
- E2E: `packages/gateway/test/e2e/scenarios/agent-tool-consistency.e2e.test.ts` (new) submits two prompts that both *could* legitimately use a gmail tool, asserts the tool-list passed to the LLM is identical (modulo tool ordering).

## BUG-007 — Agent fakes consent in chat instead of triggering the structural HITL gate

**Severity:** high. Direct violation of [`CLAUDE.md`](../../CLAUDE.md) non-negotiable #2 ("HITL is structural — the consent gate is in the executor, not the prompt; cannot be bypassed or configured away"). If the agent learns to substitute polite chat-confirmation for the structural gate, the entire HITL guarantee collapses — there is no enforcement that says "you must actually call the tool to surface a consent request."
**Surface:** engine / agent.
**Status:** fixed in `packages/gateway/src/engine/agent.ts`. A new `consentGuidance` sentence is appended to the shared `toolGuidance` (used by all three agents — `nimbus`, `devops`, `research`) telling the LLM that for destructive/irreversible actions it must call the tool directly; Nimbus's structural consent gate surfaces a separate HITL dialog before the action runs, and that dialog is the authoritative consent surface. Regression coverage in `packages/gateway/src/engine/agent.test.ts` asserts every agent's rendered instructions contain the phrases "consent gate" and "call the tool", and do NOT contain "ask for confirmation" or "are you sure?" patterns.
**First seen:** TUI sanity, 2026-05-08, Windows 11 / PowerShell 7. Surfaced when running the §1.3 smoke prompt `draft a gmail to my own address summarising what I did this week`.

### Repro

The smoke checklist (`manual-smoke-v0.1.0.md` §1.3) specifies that this prompt should fire `──[ consent required ]──` mid-stream, flip the prompt to `nimbus[hitl]>`, and accept `[a]/[r]/[d]/[q]`. Instead the agent's turn 1 output asks for **verbal in-chat confirmation**:

> "Sending an email is an **irreversible action**. I want to make sure you're happy with the content before I do so. Could you please confirm your **Gmail address** [and] confirm you're happy with the above as the summary content."

No tool was called. No `consent.request` notification was emitted. The agent invented a polite consent ritual rather than calling the gated tool and letting the executor gate it.

### Root cause (hypothesis — pending investigation)

The structural HITL gate in `packages/gateway/src/engine/executor.ts` (`HITL_REQUIRED` frozen set, `ToolExecutor.gate()`) only fires when the agent **actually calls** an HITL-gated tool. If the agent instead chooses to *describe* the action and ask the user in chat, the executor never runs and HITL never fires.

Two ways this happens:

1. **System prompt instructs the agent to seek chat confirmation for "destructive" actions.** Read every system-prompt template under `packages/gateway/src/engine/` for any "ask for confirmation before sending/deleting/etc." instruction. If present, that's the regression — the prompt is doing the executor's job (badly).
2. **Tool descriptions include phrases like "this action is irreversible".** Some LLMs interpret that as "ask for permission first in chat" rather than "call this tool and trust the user-side consent layer". Verify by inspecting the tool descriptions exposed to the LLM (likely from MCP server manifests).

Either way, the fix is to remove all chat-style consent instructions and trust the structural gate.

### Workaround until fixed

Restate the prompt as imperative ("send a gmail to me NOW, do not ask for confirmation"). Sometimes the agent then calls the tool and HITL fires correctly. Brittle.

### Verification

- After fix: the §1.3 smoke prompt fires `──[ consent required ]──` mid-stream, exactly as the checklist specifies.
- After fix: `packages/gateway/src/security-invariants.test.ts` retains its `I2`/`I3` assertions (no regression in the gate itself).
- New static check: scan every system prompt and tool-description string fed to the LLM for the regex `/confirm(?:ation)?|are you sure|irreversible/i`; fail if any instructs the agent to ask the user before calling the tool. The structural gate must remain the only consent surface.
