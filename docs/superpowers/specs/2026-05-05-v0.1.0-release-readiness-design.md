# v0.1.0 Release Readiness — Design Spec

**Date:** 2026-05-05
**Status:** Brainstormed and approved; ready for implementation-plan writing.
**Source brainstorming session:** in-conversation, 2026-05-05.

---

## Overview

Phase 4 (Presence) is code-complete on `main`. The remaining work to ship `v0.1.0` is operational (procurement + signing) plus two release-quality engineering deliverables: cross-platform install UX so `nimbus` lands on `PATH` automatically, and a user-facing documentation surface on the project's newly-registered domain.

This spec covers three independent but co-released workstreams. Each will get its own implementation plan after the spec is approved.

| ID | Workstream | Shape |
|---|---|---|
| A | Release prerequisites & cut | Operational: procurement, signing, smoke matrix, tag push |
| B | Cross-platform install scripts | Engineering: `install.ps1` + `install.sh` shipped in tarballs |
| C | User Guide expansion + custom domain | Content + light infra: extend Astro Starlight site, point `nimbus-agent.dev` at it |

Workstreams B and C are independent of each other and of A's procurement waits, and can run in parallel during the procurement lead-time. The release tag is gated by all three.

## Decisions made during brainstorming

| # | Question | Decision |
|---|---|---|
| 1 | Where do user-facing docs live? | **Extend the existing Astro Starlight site** at `packages/docs/`. No GitHub Wiki. |
| 2 | Install UX on Windows + macOS, given code-signing is deferred? | **Tarball + small unsigned `install.ps1` / `install.sh`** that copy binaries to a per-user dir and update `PATH`. Linux gets the same script for tarball/AppImage; existing `.deb` flow unchanged. |
| 3 | User Guide depth at v0.1.0? | **Tutorial + selective reference (~12–15 pages)** — covers the features that ship at v0.1.0; leaves comprehensive reference for incremental fill-in. |
| 4 | DNS plan for `nimbus-agent.dev`? | **Root → Astro docs site** via CNAME. Astro Starlight index doubles as the landing page. Subdomains (`registry.`, `telemetry.`) reserved for later. |

## Workstream B — Cross-platform install scripts

Goal: a v0.1.0 tarball user on Windows, macOS, or Linux extracts, runs **one command**, opens a new shell, and `nimbus --version` works. No manual `PATH` editing, no admin/sudo required.

### File layout

```
scripts/install/
├── windows/
│   ├── install.ps1          new — copy binaries + setx PATH (User scope)
│   └── uninstall.ps1        new — inverse of install
├── unix/
│   ├── install.sh           new — covers macOS, Linux tarball, Linux AppImage
│   └── uninstall.sh         new — inverse
├── lib/                     shared pure-function helpers (path resolution,
│   ├── paths.ts             marker-block construction, idempotency checks).
│   ├── paths.test.ts        Imported by Bun-side unit tests; the .ps1 / .sh
│   ├── markers.ts           re-implement the same logic in the shell layer.
│   └── markers.test.ts
└── README.md                user-visible: "What does this script do, why is
                             it unsigned, what does it write?"
```

### Install paths (per-user, no admin/sudo)

| Platform | Binary install dir | PATH integration |
|---|---|---|
| Windows | `%LOCALAPPDATA%\Programs\Nimbus\bin` | `[Environment]::SetEnvironmentVariable("PATH", $newPath, "User")` — direct registry write to `HKCU\Environment`. **Do not use `setx`** — `setx` truncates `PATH` at 1024 characters, which destructively wipes parts of any developer's existing `PATH`. The `.NET` API has no such limit. After the write, broadcast `WM_SETTINGCHANGE` so already-open Explorer / shell sessions can pick up the new value. |
| macOS | `~/.local/bin` (created if missing) | Idempotent block appended to `~/.zshrc`, `~/.bash_profile` (detect active login shells) |
| Linux tarball + AppImage | `~/.local/bin` | Same idempotent rc-block as macOS |
| Linux `.deb` | `/usr/local/bin` (existing — unchanged) | Already handled by dpkg's wrapper-in-`/usr/local/bin` from `package-linux-installers.ts` |

### Idempotency contract

- Re-running `install` on an existing install:
  - Detects existing copy via the install dir + the marker block in the rc file.
  - Asks confirm before overwriting (skippable with `--yes` / `-y`).
- `uninstall`:
  - Removes binaries.
  - Removes the rc-block by sentinel comment markers — never touches lines outside the markers.
  - Markers (literal): `# >>> nimbus PATH >>>` and `# <<< nimbus PATH <<<`.
- Dry-run flag (`--dry-run`) prints planned actions, exits without writing.

### Bundling into release artefacts

`release.yml` packages the appropriate platform script into each tarball:

| Artefact | Bundled installer |
|---|---|
| `nimbus-<ver>-windows-x64.zip` | `install.ps1` + `uninstall.ps1` at the root |
| `nimbus-<ver>-macos-arm64.tar.gz` / `-x64.tar.gz` | `install.sh` + `uninstall.sh` at the root |
| Linux `tar.gz` headless bundle | Same `install.sh` + `uninstall.sh` |
| Linux AppImage | `install.sh` + `uninstall.sh` ship alongside (sibling files) |
| Linux `.deb` | unchanged |

### Security note

- Windows: `setx` writes to `HKCU\Environment` only — no admin, no SmartScreen prompt for the registry write itself. The `.ps1` is unsigned but plaintext; users must invoke explicitly (`.\install.ps1`).
- macOS / Linux: shell scripts are plaintext and POSIX-portable; no Gatekeeper involvement.
- Both scripts print a clear "About to write to `<file>` and `<dir>`. Continue? [y/N]" prompt unless `--yes` is passed.
- The bundled `README.md` documents exactly what each script writes and how to undo it.

### Testing

- **Bun unit tests** (`scripts/install/lib/*.test.ts`) for the pure helper logic: path resolution, marker-block construction, idempotency detection. Targets the shared `.ts` helpers — the `.ps1` / `.sh` mirror the same logic with thin parity tests.
- **CI smoke jobs** — one per OS in a new `.github/workflows/install-smoke.yml`:
  1. Build a fresh tarball.
  2. Extract into a clean temp dir.
  3. Run the bundled install script with `--yes`.
  4. Spawn a fresh shell.
  5. Assert `nimbus --version` exits 0 and prints the expected version.
  6. Run uninstall; assert binaries gone and the rc file no longer contains the marker block.
- **Coverage gate:** `scripts/install/lib/` ≥ 80% lines.

## Acceptance criteria

A1. All seven GHA secrets from the runbook §7.5 present.
A2. `release.yml` dry-run on `v0.1.0-rc1` succeeds end-to-end; signed Linux `.deb` and AppImage; unsigned but `SHA256SUMS.asc`-signed Win/Mac tarballs.
A3. `packages/gateway/src/updater/public-key.ts` holds the production Ed25519 public key (not the dev key).
A4. `docs/release/SIGNING-KEY.asc` committed with real bytes.
A5. `manual-smoke-v0.1.0.md` results matrix fully ✅/⚠ on every supported platform.
A6. `vscode-v0.1.0` and `v0.1.0` tags pushed; release artefacts publicly downloadable.

B1. Fresh user on Windows / macOS / Linux extracts the v0.1.0 tarball, runs the bundled install script with `--yes`, opens a new shell, runs `nimbus --version`, sees the version string. No manual PATH editing.
B2. Re-running `install.ps1` / `install.sh` on an existing install is idempotent (prompts before overwriting; `--yes` accepts).
B3. `uninstall.ps1` / `uninstall.sh` removes binaries and the rc-block by sentinel markers without touching lines outside the markers.
B4. `scripts/install/lib/` ≥ 80% line coverage; CI smoke jobs green on all three OSes.

C1. `nimbus-agent.dev` resolves to the Astro Starlight site over HTTPS.
C2. Sidebar shows three top-level sections (User Guide, Reference, Developer) populated as specified.
C3. All ~12–15 User Guide pages live; each carries at least one worked example or screenshot where applicable.
C4. Existing pages re-bucketed into Reference / Developer; no broken links.
C5. `deploy-docs.yml` final smoke step passes against `https://nimbus-agent.dev/`.

## Out of scope

- macOS Apple Developer Program enrollment + notarization workflow.
- Windows EV Authenticode certificate procurement.
- **Operating a telemetry collector** at `telemetry.nimbus-agent.dev`. The default endpoint stays in `packages/gateway/src/config/telemetry-toml.ts` as documented. Telemetry is **opt-in** (`enabled = false` default) and the implementation must degrade silently on flush failure — opted-in users will see failed flushes until the collector exists, which is acceptable noise for v0.1.0. (Implementation plan should include a one-line spot-check that the failure path is silent and bounded — no infinite retry loop.)
- Hosting `registry.nimbus-agent.dev` (Phase 5 / v0.1.1+).
- **Operating a separate updater manifest host.** The updater URL is already wired to `https://github.com/asafgolombek/Nimbus/releases/latest/download/latest.json` in `packages/gateway/src/config/nimbus-toml.ts:408`. `release.yml` must publish this `latest.json` file as part of every release. No subdomain (`releases.` or `updates.`) is needed.
- **`@nimbus-dev/sdk`** and **`@nimbus-dev/client`** version alignment. Both are independent release artefacts on their own tag prefixes (`client-v*`); SDK at `1.0.0` signals public-API stability for extension authors. They do not get retagged for `v0.1.0`.
- **Tauri version bumps.** Currently pinned at Rust `2.10.3` + JS `^2.11.0`. Owned by Dependabot, not a release-cut decision.
- Multi-language docs (English only).
- A separate marketing landing page distinct from the docs (the Astro Starlight index serves both).
- GitHub Wiki.
