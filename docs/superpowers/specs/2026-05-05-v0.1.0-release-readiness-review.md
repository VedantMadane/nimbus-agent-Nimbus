# Review: v0.1.0 Release Readiness Design Spec

**Date:** 2026-05-05
**Reviewer:** Gemini CLI

---

## 1. Summary of findings

The design spec for `v0.1.0` is comprehensive and aligns well with the existing project state. Workstreams A, B, and C address the critical path for a public launch. The documentation (especially `docs/README.md` and the smoke checklist) is exceptionally detailed.

## 2. Workstream A: Release prerequisites & cut

### Observations
- `nimbus-agent.dev` is already registered (as of 2026-05-05).
- The Ed25519 updater infrastructure is ready (`scripts/generate-updater-keypair.ts`, `scripts/sign-ed25519.ts`).
- **Minor inconsistency:** The root `package.json` lists version `1.1.0`, while sub-packages (gateway, cli) list `0.1.0`. This should be reconciled before tagging `v0.1.0`.

### Suggestions
- **Version Alignment:** Ensure all `package.json` files (root + workspaces) are set to `0.1.0` before the release cut to avoid confusion in release artifacts.
- **Tag Order:** The spec proposes tagging `vscode-v0.1.0` first. Since the VS Code extension depends on the Gateway, ensuring the Gateway artifacts are available (or at least the version is locked) is important. The current order is likely fine as the extension is a client, but worth a quick double-check.

---

## 3. Workstream B: Cross-platform install scripts

### Observations
- `scripts/install/` is currently non-existent, making this a greenfield engineering task.
- The use of marker blocks (`# >>> nimbus PATH >>>`) for shell profile idempotency is a robust best practice.

### Open Questions / Risks
- **Windows `PATH` Truncation:** The spec mentions using `setx PATH` on Windows. `setx` has a 1024 character limit. For users with long existing `PATH` variables, `setx` can truncate the entire `PATH`, causing system-wide issues.
    - **Suggestion:** Use PowerShell to modify the registry directly (`HKCU:\Environment`) or append to the current session and persistent `PATH` using `[Environment]::SetEnvironmentVariable`.

---

## 4. Workstream C: User Guide & custom domain

### Observations
- `packages/docs/astro.config.mjs` currently uses `base: "/Nimbus/"`. The transition to `base: "/"` is correctly identified in the spec.
- `docs/README.md` is a goldmine for User Guide content; much of it can be reused or linked directly.

### Suggestions
- **Search & Replace:** Beyond literals in `packages/docs/`, check if any hardcoded documentation links exist in `packages/ui` (Tauri app) or `packages/cli` that might need updating to the new `nimbus-agent.dev` domain.
- **Favicon / Branding:** Ensure the custom domain site has a consistent favicon and metadata (OpenGraph tags) for `nimbus-agent.dev`.

## 5. Miscellaneous

- **Tauri Stable:** Confirm if the `v0.1.0` release targets a specific stable version of Tauri 2.0.
- **Telemetry Endpoint:** While `telemetry.nimbus-agent.dev` is deferred, ensure the default endpoint in `nimbus.toml` and the gateway logic is pointed at a sensible "empty" or "localhost" default if not ready, to avoid error noise for users.
